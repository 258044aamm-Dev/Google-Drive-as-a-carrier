# YAOS project issue investigation — google-drive-carrier

Inspected checkout `02d0068` (branch `google-drive-carrier`) and the four issues in the YAOS Linear project on 2026-10-17. This is a proposed fix, **not an implementation**; no live multi-device/Obsidian verification was performed. COD-8 and COD-9 are already marked Done in Linear; COD-10 and COD-11 are Todo.

## Priority 0 — COD-10: wrong Drive folder selected, then sync halted

The two quoted messages are consistent with one chain: `resolveVaultFolder()` chooses the *oldest* same-name folder when there is no usable remembered ID (`src/drive-carrier/driveFolders.ts:140-181`), independently of its `meta.json`. `prepareFolder()` then calls `keyring.ensureMeta()` (`src/drive-carrier/driveTransport.ts:813-839`); `readMeta()` rejects a differing vault ID (`src/drive-carrier/driveKeyring.ts:164-172`). That rejection is an intentional safety barrier: do not bypass it or edit a remote vault ID to force a merge. The duplicate warning is emitted **before** validation, so “folder in use” is premature; the warning and the fatal error can both be true. Note also that a saved usable folder ID wins without checking its name, as intended for renamed folders. If that ID belongs to the wrong vault, the same fatal barrier applies.

**Fix:** Make folder resolution identity-aware while preserving the keyring's final authoritative check. For same-name candidates, inspect each readable `meta.json` before selection; prefer a verified match for the configured vault ID (with deterministic oldest/id tie-break among matches). Do not auto-select a verified *different* vault. Treat unreadable/absent/legacy metadata as unknown, not as a match; define a conservative, explicit creation/join policy for this case, with a user-facing decision when ambiguous. If a remembered folder ID is known to mismatch, stop and explain how to clear/reselect it; do not silently change the pin. Persist a chosen folder ID only **after** metadata validation succeeds (currently this happens after `ensureMeta()`, which is good). Correct the duplicate wording to distinguish candidate versus validated active folder. Never delete duplicate folders automatically.

**Important boundary:** `drive.file` scope (`src/drive-carrier/googleAuth.ts`) limits which files a particular Google OAuth client can see. A different client may not see the prior folder at all. No sorting algorithm fixes invisible data: use the same OAuth client on all devices or provide an explicit Drive folder access/migration workflow with appropriate consent/scopes. Confirm the two clients, visible folder IDs, stored `driveFolderId`, and `meta.json` vault IDs before any cleanup. Do not copy the quoted vault IDs into a new setup as a guess.

**Tests:** mock two same-name folders (oldest wrong ID, newer matching ID), multiple matching folders, old metadata without ID, unreadable metadata, valid/mismatched saved ID, OAuth-client invisible folder, concurrent creation. Assert no writes to a mismatched folder, no automatic deletions, deterministic choice, and persisted ID only after validation.

## Priority 1 — COD-11: header and bottom-right status truth

Both indicators are drawn from the **same** `toSimpleStatus()` result in `src/main.ts:1942-1985`; the header is updated at `:1970` and the bottom bar at `:1985`. Thus they are not independently hard-coded, although the optional detailed bottom-bar mode intentionally uses a different *label*. Provider status changes call `refreshStatusBar()` via `ConnectionController.setupProviderStatusHandler()`; receipt refreshes are coalesced. This does not prove their semantic accuracy.

**Concrete gaps:** `updateStatusBar()` returns immediately when there is no status-bar element (`src/main.ts:1943`), so a header-only display could miss updates. More importantly, Drive fatal errors set `DriveTransport.fatalError`, stop its timers, mark it offline and raise a transient Notice (`src/drive-carrier/driveTransport.ts:655-663`; `src/main.ts:2720-2734`), while `ConnectionController.getState()` only classifies the sync engine's `fatalAuthError`, readiness, reconciliation and `connected` (`src/runtime/connectionController.ts:139-177`). A stopped Drive transport can therefore appear merely **Offline** instead of **Error** after the toast expires. Also `toSimpleStatus()` falls through to “Synced” for an online connection when receipt is null/unknown (`src/status/simpleStatus.ts`), although online alone does not prove remote durability or attachment completion. `computeSyncStatus()` detects IndexedDB error, but `updateStatusBar()` preferentially supplies the rich connection state to `toSimpleStatus()`, potentially masking the coarse `error`.

**Fix:** Build one carrier-aware status snapshot at refresh time (connection, fatal carrier reason, local persistence fault, reconciliation, pending writes/receipts, transfer and conflicts); have both renderers consume it. Remove the status-bar-element early return from snapshot calculation; render whichever surfaces exist. Rank persistent fatal/persistence failures above offline and busy, and represent unconfirmed/unsupported receipt as “Connected” or “Checking”, not “Synced”. Preserve detailed bottom-bar text and existing icon styles. Wire Drive fatal transitions to refresh even when provider event order changes; clear them only after genuine recovery/reinitialization. Keep status claims modest: a server receipt does not prove another device has received the change.

**Tests:** header-only and both surfaces; startup, connection loss/reconnect, Drive wrong-vault fatal, auth failure, IndexedDB failure, receipt pending/unknown/confirmed, transfers and conflicts; assert simultaneous transitions and no stale green after fatal. Real Obsidian desktop/mobile smoke test remains necessary.

## Already completed — COD-9 and COD-8

COD-9's setup row is gated by `!isDriveSignedIn(this.host.settings)` in `src/settings/settingsTab.ts:723-734`; `isDriveSignedIn()` checks credentials/token presence in `src/drive-carrier/carrierSettings.ts:100-103`. Recheck in the running UI after wizard completion, sign-out and carrier switches; credential presence is **not** proof that an OAuth token remains usable or that vault initialization succeeded. If the reported link is still visible, identify whether it is this settings row or a different setup link and test the settings re-render on wizard completion before altering the predicate.

COD-8's carrier handler now prompts **before** saving, handles cancel and save/prepare failures, and gives a reload Notice (`src/settings/settingsTab.ts:1101-1147`); the repository also has `docs/COD-8-carrier-switch-warnings.md`. Do not reimplement the already completed workflow without a reproduced regression.
